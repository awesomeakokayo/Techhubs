## 5. Knowledge checks and answer keys (internal)

### Stage 1 — Product Thinking Foundations (3 questions)

1. Which is the PM's responsibility rather than the engineer's?
   - · Choosing implementation details
   - **✔ Deciding what to build and why**
   - · Writing code
   - · Provisioning servers
   - _Why:_ PM owns what and why; engineering owns how. · _level: understand_
2. What does Jobs To Be Done focus on?
   - · Features competitors ship
   - **✔ The progress a user is trying to make in a situation**
   - · Pricing only
   - · Design style
   - _Why:_ JTBD frames needs as the progress a user seeks, not as features. · _level: understand_
3. Which is an outcome rather than an output?
   - · A shipped feature
   - **✔ An increase in weekly active users**
   - · A new design system
   - · A release date
   - _Why:_ Outcomes are changes in behaviour/results; outputs are things you ship. · _level: apply_

### Stage 2 — User Research & Discovery (3 questions)

1. The Mom Test says to…
   - · Ask if your idea is good
   - **✔ Ask about the user's actual past behaviour and problems, not your idea**
   - · Survey at scale
   - · Avoid talking to users
   - _Why:_ Honest feedback comes from discussing real past behaviour, not your idea. · _level: understand_
2. Which is a leading question?
   - · "Walk me through the last time this happened."
   - **✔ "Wouldn't this feature be useful to you?"**
   - · "What did you do next?"
   - · "How often did this occur?"
   - _Why:_ Suggesting the answer biases the response; ask about actual behaviour instead. · _level: evaluate_
3. What is assumption mapping for?
   - · Decorating slides
   - **✔ Surfacing the riskiest beliefs to test before committing to build**
   - · Estimating cost
   - · Choosing a font
   - _Why:_ Assumption mapping prioritises which beliefs to validate first. · _level: apply_

### Stage 3 — Strategy & Prioritisation (3 questions)

1. What makes a good key result?
   - · A task to complete
   - **✔ A measurable outcome with a target and timeframe**
   - · A list of features
   - · A budget
   - _Why:_ Key results are measurable outcomes, not tasks. · _level: understand_
2. Which RICE factor captures how many users an initiative affects?
   - **✔ Reach**
   - · Impact
   - · Confidence
   - · Effort
   - _Why:_ Reach is the number of users affected in a period. · _level: recall_
3. The Kano model distinguishes…
   - · Cost from price
   - **✔ Must-have, performance and delighter attributes**
   - · Agile from Waterfall
   - · Users from buyers
   - _Why:_ Kano separates basic needs, performance features and delighters. · _level: understand_

### Stage 4 — Writing Product Requirements (3 questions)

1. What belongs in a PRD?
   - · Only the feature name
   - **✔ Problem, scope, user stories, acceptance criteria, metrics and edge cases**
   - · The code
   - · The colour palette
   - _Why:_ A PRD aligns the team on problem, scope and measurable success. · _level: understand_
2. A good acceptance criterion is…
   - · Vague
   - **✔ Specific and testable**
   - · A design description
   - · Optional
   - _Why:_ Acceptance criteria must be verifiable so QA and engineering agree. · _level: apply_
3. Why list edge cases before engineering starts?
   - · To add work
   - **✔ To surface ambiguity early, reducing rework and missed scenarios**
   - · It is required
   - · To slow delivery
   - _Why:_ Identifying edge cases up front prevents costly surprises. · _level: evaluate_

### Stage 5 — Growth & Engagement Metrics (3 questions)

1. What does the AARRR framework stand for?
   - · Analyse, Adapt, Repeat, Report, Review
   - **✔ Acquisition, Activation, Retention, Referral, Revenue**
   - · Awareness, Ads, Reach, ROI, Results
   - · Audit, Assess, Refine, Release, Retire
   - _Why:_ AARRR is acquisition, activation, retention, referral, revenue. · _level: recall_
2. When is DAU the more meaningful metric than MAU?
   - **✔ For a product used daily, like messaging**
   - · For a product used annually
   - · Never
   - · Only for free products
   - _Why:_ DAU matters for habitually used products; MAU suits lower-frequency ones. · _level: apply_
3. NPS is best used as…
   - · The single source of truth
   - **✔ A directional relationship signal alongside behavioural metrics**
   - · A revenue forecast
   - · An A/B result
   - _Why:_ NPS is directional sentiment, not a behavioural truth. · _level: evaluate_

### Stage 6 — Retention, Funnels & Experiments (3 questions)

1. What does a flattening retention curve indicate?
   - **✔ Product-market fit signal: a core of users stays**
   - · The product is failing
   - · Users are churning completely
   - · Nothing useful
   - _Why:_ A flattening curve suggests a retained core audience. · _level: analyze_
2. Funnel analysis is used to…
   - · Increase prices
   - **✔ Find the stage where users drop off most so you can improve it**
   - · Design logos
   - · Write copy
   - _Why:_ Funnels locate the biggest drop-off to prioritise improvement. · _level: apply_
3. Which makes an A/B test result trustworthy?
   - · Stopping as soon as a leader appears
   - **✔ A pre-defined success metric, sufficient sample and a full test duration**
   - · Changing several variables
   - · Testing on a tiny sample
   - _Why:_ Pre-registration, adequate sample and duration make results reliable. · _level: evaluate_

### Stage 7 — Shipping with Engineering (3 questions)

1. What should an engineering ticket contain?
   - · A one-line title only
   - **✔ Context, requirements, acceptance criteria and out-of-scope notes**
   - · A design mockup only
   - · A deadline only
   - _Why:_ Clear tickets include context, acceptance criteria and boundaries. · _level: apply_
2. MVP means…
   - · The lowest quality thing possible
   - **✔ The smallest release that delivers real value and lets you learn**
   - · A finished v1
   - · A prototype with no users
   - _Why:_ An MVP delivers real value and enables learning, not minimum quality. · _level: understand_
3. What is the purpose of a launch checklist?
   - · To delay launch
   - **✔ To ensure monitoring, rollback and ownership are ready before release**
   - · To add paperwork
   - · To replace testing
   - _Why:_ Launch checklists ensure operational readiness and rollback. · _level: understand_

### Stage 8 — PM Career & Portfolio (3 questions)

1. A strong PM case study emphasises…
   - · Pretty screens
   - **✔ The problem, decisions, trade-offs and measured outcome**
   - · A long introduction
   - · Tool names
   - _Why:_ Credibility comes from reasoning and evidence, not visuals alone. · _level: evaluate_
2. APM (Associate Product Manager) programmes are designed for…
   - · Senior PMs
   - **✔ People entering product management with little or no PM experience**
   - · Engineers only
   - · Designers only
   - _Why:_ APM programmes target early-career entrants to PM. · _level: recall_
3. In a product-sense interview, the most important skill is…
   - · Memorising frameworks
   - **✔ Structuring your thinking and justifying trade-offs for a specific user**
   - · Speed
   - · Using buzzwords
   - _Why:_ Interviewers look for structured reasoning and user-centred trade-offs. · _level: evaluate_

### Stage 5 — Build: Growth Metrics & Funnel Dashboard

- **Problem:** A product team measures activity but not the funnel that drives growth.
- **Audience:** A product team and its stakeholders.
- **Required functionality:**
  - A North Star metric and 2–3 supporting metrics with definitions
  - A funnel map with stage volumes
  - Identification of the largest drop-off with a hypothesis
  - A one-page dashboard mock
- **Acceptance criteria:**
  - Metric definitions are unambiguous
  - The funnel identifies a specific weak stage
  - The dashboard communicates one clear insight
- **Required evidence:**
  - A metrics definition document
  - The funnel analysis
  - A dashboard mock with the headline insight
- **Constraints:**
  - Every metric must have a precise definition and data source
  - Guardrail metrics must be included

### Stage 6 — Build: Experiment Design & Readout

- **Objective:** Design a controlled experiment and commit to a pre-registered decision rule.
- **Problem:** A product change is shipped on opinion rather than evidence.
- **Audience:** A product team deciding whether to invest in a change.
- **Required functionality:**
  - A falsifiable hypothesis
  - A primary metric, guardrail metrics, and a success threshold
  - Sample/segment plan and duration
  - A pre-committed decision rule (ship/iterate/stop)
- **Acceptance criteria:**
  - The hypothesis is testable and specific
  - The success threshold is justified
  - The readout applies the rule to realistic results
- **Required evidence:**
  - An experiment design document
  - A readout using (real or realistic) results
  - The final recommendation
- **Constraints:**
  - Decision rule must be set before results
  - Guardrails must be able to block a launch

### Stage 7 — Build: Feature Ship Case Study

- **Objective:** Take one feature from spec to launch and reflect on the outcome.
- **Problem:** Features slip between a good spec and a working launch.
- **Audience:** A product team and an engineering partner.
- **Required functionality:**
  - Engineering-ready requirements with acceptance criteria
  - Trade-off notes (scope, quality, time)
  - A launch/rollout plan with metrics to watch
  - A retrospective on what changed after feedback
- **Acceptance criteria:**
  - Acceptance criteria are objectively checkable
  - The rollout plan states success and failure signals
  - The retrospective is candid about what changed
- **Required evidence:**
  - The spec
  - The rollout plan
  - The retrospective
- **Constraints:**
  - Requirements must be testable
  - Must include a rollback/kill-switch plan

## 10. Areas requiring human review

- **Subject matter:** factual accuracy, currency and depth of each lesson, resource and knowledge check.
- **Pedagogy:** whether the worked example and resource actually prepare the learner for the knowledge check and project.
- **Accessibility:** captions/transcripts, contrast, keyboard use and screen-reader behaviour of the learning UI.
- **Assessment quality:** plausibility of distractors, whether questions test understanding rather than recall, fairness of rubric weights and the pass threshold.
- **Sign-off:** record a genuine, named review in `docs/curriculum-quality-signoff.json`. No track is approved until then.

## 11. Exact criteria for passing

A track becomes **premium-approved** only when ALL of the following hold. Failing any one blocks approval, even when the aggregate scores are high. 90 is a floor per score, not compensation for a failed gate.

- Mechanical: readiness ≥ 90 (this track: 99.5) **and** worthiness ≥ 90 (this track: 98.9).
- Mandatory quality gates: all pass (this track: pass).
- Every stage: at least one required resource verified to content-inspected (level 3) or better.
- Every stage: a valid knowledge check with a correct answer key, plausible distractors and server-side grading.
- Every progression-bearing section: an AI-verified mastery rubric anchored to the section objective, with source inspection where required.
- Every phase: a project with a brief, required evidence and acceptance criteria.
- A genuine, named **human** sign-off in `docs/curriculum-quality-signoff.json`.

**Would fail review if:** a required resource 404s or teaches a different objective; an answer key is wrong; a rubric can be passed without the required evidence; a mandatory criterion is waived by a high aggregate score; a project has no acceptance criteria or evidence; or a video is claimed watched without playback verification.
